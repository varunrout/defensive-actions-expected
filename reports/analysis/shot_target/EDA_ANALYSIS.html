Bottom line up front

Both datasets show the same dominant signal: proximity to either box (is_in_defending_box, is_in_attacking_box) and phase (box_defence, high_press_proxy) are associated with roughly double the base shot rate, consistently across active and passive tables. The active dataset's distance/count features are usable again after a real bug fix -- nearest_defender_distance and its correlated siblings were previously self-referencing the acting player (fixed; verified 0.0% residual). Camera-coverage metadata is excluded outright because it correlates with shots for a reason that has nothing to do with defending. After every exclusion, 51 active and 44 passive candidate features remain, unpruned for redundancy -- that's the next pass.

1. Overview

player_defensive_actions.parquet (active) passive_defense.parquet (passive)
Grain one row per actual defensive action one row per visible defender-slot per on-ball attacking event
Rows 56,068 1,593,181
Base rate (target_future_shot_10s mean) 7.79% 5.97%

The two tables are modelled separately because their grains are disjoint and not nestable: the active table has one row per thing a defender actually did, while the passive table has one row per defender who was merely present (possibly doing nothing) for every visible on-ball attacking event -- a single active action can correspond to zero, one, or several passive rows for teammates who weren't the actor. Pooling them would double-count positioning context and conflate "did something" with "was positioned somewhere."

2. Methodology

  • Categorical shot rate: df.groupby(col)['target_future_shot_10s'].agg(n='count', shots='sum', rate=lambda s: s.mean()*100) -- always a groupby-mean against the full row population per category, never filter-to-shots-then-distribute.
  • Boolean lift: rate_true - rate_false in percentage points, where each rate is df.loc[df[col]==True/False, target].mean()*100. pct_true = df[col].mean()*100. Any True or False group with n < 500 is flagged small-n, not excluded.
  • Continuous distributions: 24 equal-width bins from the column min to its 99th percentile (np.percentile(x, 99)); rows above p99 are counted as n_extreme and reported with the true max, never dropped from the histogram population or from mean/median/skew (scipy.stats.skew), which are computed on the full unclipped column.
  • Discrete distributions: raw value counts capped at 20 distinct values, tail bucketed beyond that.

Every relationship in this report is a correlation or association, never a cause -- that includes every header, table caption and finding below, with no exceptions.

The nearest_defender_distance self-reference bug

StatsBomb 360 freeze frames include the acting player's own position, marked "actor": true. Before the fix, _support_features in src/dax/features/player_defense.py treated that entry as an ordinary support player, so a defender's distance to their own action was measured as their distance to themselves -- nearest_defender_distance was effectively ~0m in 73.6% of rows. The same root cause, via the attacker branch of the same freeze-frame split, produced the identical pattern in nearest_attacker_distance for 20.0% of rows (Ball Recovery/Interception events where the recovering player is on the attacking side).

Fix: _exclude_actor_from_frame now strips the actor: true entry before the attacker/defender split, for every column built from that candidate pool -- nearest_attacker_distance/nearest_defender_distance, attacker_centroid_x/y/defender_centroid_x/y, attacker_spread/defender_spread, visible_attacker_count/visible_defender_count, attackers_within_5m/10m/defenders_within_5m/10m, local_numerical_balance_5m/10m, attacker_defender_ratio, defenders_between_ball_and_attacking_goal.

Verified fixed, directly against the current parquet:

  • Rows with nearest_defender_distance < 0.01m: 0 of 56,068 (0.0%), down from 73.6%.
  • Rows with nearest_attacker_distance < 0.01m: 0 of 56,068 (0.0%), down from 20.0%.
  • nearest_defender_distance now has mean 9.49m, median 6.35m, skew 4.38 -- right-skewed but consistent with genuine on-pitch spacing, not a ~0m spike.

defender_centroid_x/y and defender_spread (and their attacker-side counterparts) were built from the same corrected candidate pool and checked directly: defender_centroid_x ranges 0.04-119.10 with no near-zero clustering, and the 244 rows where defender_spread == 0.0 (198 for attacker_spread) are single-visible-defender/attacker frames where a spread of zero is the correct value, not a residual self-reference artifact -- cleared.

4. What was excluded, and why

Column(s) Reason
visibility_quality_band, visibility_limited, ball_inside_visible_area, action_inside_visible_area, local_5m_region_fully_visible, local_10m_region_fully_visible, visible_area_polygon_area, visible_area_fraction_of_pitch Camera/360-tracking-coverage metadata, not a football signal. These show real statistical lift with shots, but that's a confound: crowded, high-danger zones (own-box scrambles, counters) are simultaneously harder for the 360 tracking to fully capture and where shots cluster. The lift is about camera coverage, not defending.
action_changed_possession, action_ended_possession, action_won_possession (active only) Structural zero: exactly 0.00% shot rate by the target-window definition itself, not a genuine finding.
freeze_frame_count Data-collection artifact, not a defensive feature.
carrier_x/carrier_y (passive) Verified 100%-identical to ball_x/ball_y (the on-ball event's location is the ball location in this table) -- dropped, with ball_x/ball_y kept as canonical.

Open item, not buried in a footnote: action_x/action_y (active) are still a known unresolved duplicate. They are verified 100%-identical to ball_x/ball_y in the current dataset -- the report generator's check_duplicate_columns assertion confirmed this again on this pass and would fail loudly if it ever stopped being true. They should be dropped, the same way carrier_x/carrier_y already were, but haven't been: they're required/canonical column names across 11 files in the modelling and analysis pipeline (dax.models.schemas/specs/leakage, baseline_regression.py, baseline_logistic.py, dax.analysis.*, dax.coach_analysis.zones, analysis.player_features.*), and dropping them needs a coordinated rename across all of those -- a separate, dedicated task, tracked by tests/test_player_defense_geometry.py::test_no_duplicate_columns_on_real_player_defensive_actions_dataset, which enforces that action_x/ball_x and action_y/ball_y are the only allowed duplicate pair.

6. Open items / next steps

  1. Cross-correlation testing across both final feature lists -- not yet done. Candidate redundant pairs already visible from lift alone: is_central_lane/is_wide_lane, is_deep_zone/is_high_zone (active).
  2. Resolve the action_x/action_y duplicate drop (Section 4) -- requires a coordinated rename across 11 downstream modules; currently guarded only by a test asserting the duplicate is the only allowed exception.
  3. Small-n boolean lifts to treat with caution before modelling: has_visible_attacker (active, False n=31), has_visible_defender (active, False n=76), has_option_2 (passive, False n=279).
  4. n_extreme at ~1% is mechanical, not a red flag -- every continuous column's extreme count is a direct consequence of the p99 clip definition; no column showed an anomalously large extreme population worth a separate follow-up.
  5. No causal claims anywhere in the modelling writeup that follows this document -- every finding above is correlational only, per Section 2.
